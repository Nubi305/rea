# clients

## Summary

Claude Code (the only client I could read in full) offers the surfaces REA needs: plugins that bundle skills, subagents, hooks, MCP servers and a bin/ folder; a headless claude -p with JSON output, a JSON schema for the verdict, plugin and MCP status in the init event, and per-model usage that includes subagents. Its context levers are documented with numbers: skill descriptions are capped at 1,536 characters in the listing, invoked skill bodies are re-injected after compaction at 5,000 tokens each and 25,000 in total, and tool search defers MCP tools by default. In auto mode, deferral starts when deferrable tool definitions reach 10% of the context window, and each search loads up to 5 tools. For REA's roughly 255 tools this means the default already keeps schemas out of context, so the open lever is the tool descriptions and search keywords, not switching deferral on. Large outputs are also handled: a valid Bash result goes inline up to about 30,000 characters and spills to a file beyond that, and a hook's output over 10,000 characters is saved with a 2,000-character preview. Two constraints matter for design. Plugin subagents ignore their own hooks, mcpServers and permissionMode, and a bare -p run skips hooks and MCP servers unless they are passed on the command line. Codex, Cursor and most of Gemini CLI could not be checked: developers.openai.com, cursor.com and geminicli.com did not resolve from this session, so only the GitHub copies of the Codex and Gemini docs were read, and Cursor is entirely unconfirmed. I ran no measurements; every fact below is documented or source-derived, and none is ran-it. Nothing was written to disk because this session had no shell tool.

## Already good (7)

- REA already fits the Claude Code plugin model: a plugin can bundle skills, MCP servers (.mcp.json), hooks (hooks/hooks.json) and an executable bin/ folder on the Bash PATH, so the REA CLI can be called without any MCP schema in context. Confirmed by https://code.claude.com/docs/en/plugins-reference.md (Standard layout).
- Tool search is the default for Claude Code MCP tools (ENABLE_TOOL_SEARCH unset means on), so a 255-tool MCP catalogue is already deferred rather than sent every turn. Confirmed by https://code.claude.com/docs/en/agent-sdk/tool-search.md.
- The headless path has what an evaluation harness needs: --output-format json or stream-json, --json-schema with structured_output, --max-turns, --max-budget-usd, --permission-mode, --allowedTools/--disallowedTools, --plugin-dir, --mcp-config, --resume and --session-id. Confirmed in https://code.claude.com/docs/en/headless.md and https://code.claude.com/docs/en/cli-reference.md.
- The stream-json init event lists loaded plugins, plugin_errors, MCP server status and mcp_server_errors, so a CI run can fail when REA's MCP server does not connect. Confirmed in https://code.claude.com/docs/en/headless.md (Fail CI when a plugin or MCP server doesn't load).
- Subagents already give context isolation: a subagent's large reads stay out of the parent and only its summary returns. Confirmed in https://code.claude.com/docs/en/sub-agents.md and https://code.claude.com/docs/en/context-window.md.
- Compaction-aware design is already documented: CLAUDE.md at project root and skill bodies survive compaction (skill bodies capped at 5,000 tokens each), and subagent transcripts are stored apart from the parent. Confirmed in https://code.claude.com/docs/en/context-window.md (What survives compaction).
- Plugin hooks also run inside subagents, and a PreToolUse hook can return permissionDecision deny. That gives REA a way to block destructive or out-of-scope calls for a given run without touching the agent prompt. Confirmed in https://code.claude.com/docs/en/hooks.md (For subagents; PreToolUse permission decisions).

## Opportunities (7)

### Keep skill descriptions short and the team playbook's skill bodies under the 5,000-token re-injection cap

- problem: A skill's description is in context on every turn (listing truncated at 1,536 characters), and a skill body is re-injected after compaction only up to 5,000 tokens each and 25,000 tokens in total, with the oldest dropped first. A large playbook or REA skill that exceeds these limits silently loses its tail after /compact, and every turn carries every description. The current size of REA's skill descriptions and bodies has not been measured.
- proposal: Measure the skill listing and each invoked skill body in the fork (skill files live in the REA skill folder; the team playbook is in the skill). Trim each description to fewer than 1,536 characters, keep the most important instructions in the first 5,000 tokens of SKILL.md, and move detail into on-demand reference files that the skill names. No feature changes.
- expected gain: Fewer tokens loaded on every turn for each installed REA skill, and no silent truncation after compaction. The size of the gain depends on the measured current sizes, which I could not check because this session had no shell tool.
- effort: small
- risk: Shorter descriptions can reduce skill triggering accuracy. Judge it with a trigger test: for a fixed set of 20 REA tasks, count how often the intended skill is invoked before and after the change. A drop would show as a lower hit rate.
- judge: Run `claude -p` on the same 20 tasks before and after, with stream-json output. Count the Skill tool_use events and total_cost_usd (from modelUsage). Expect equal or better trigger rate and a lower input-token total. The check is 20 headless runs, which is light.

### Give REA's tool catalogue an explicit deferral strategy: keep a small always-loaded core and make search work on keywords

- problem: With about 255 tools, tool search defers them by default, but search returns only the 5 most relevant per query, and each search costs a round trip. After compaction the agent must search again. The docs say tool selection degrades past 30-50 loaded tools, so the search quality of tool names and descriptions decides how often an agent is misled. REA's current search quality has not been measured.
- proposal: Measure the current behaviour first: with REA's MCP server connected, read the deferred tool summary and tool-search result counts in a stream-json run. Then pick a core of 5-10 tools an agent needs on every task (for example rea status, the target open and the report call) and mark them alwaysLoad. Give every other tool a name and description with specific keywords so search finds it. Do not change the 255-tool catalogue itself.
- expected gain: Fewer input tokens per turn for a typical REA task, and fewer wasted search round trips. The gain has to be measured. The expected direction is lower modelUsage.inputTokens per task.
- effort: medium
- risk: alwaysLoad on too many tools removes the saving. Search on poor keywords hides tools the agent needs. The exact alwaysLoad semantics and the MCP tool-search section of the Claude Code MCP page were not readable here, so confirm them against https://code.claude.com/docs/en/mcp.md before building on them.
- judge: A/B on 10 fixed REA tasks: ENABLE_TOOL_SEARCH=false (every definition loaded) against the default with alwaysLoad on the core set. Compare modelUsage inputTokens and total_cost_usd, and count tool-search calls. Also check that every task still succeeds. The check is 20 headless runs.

### Ship the REA CLI in the plugin's bin/ folder and keep the MCP server for the cases that need it

- problem: Every MCP tool definition costs context when it is loaded, and tool search only defers that cost. A plugin's bin/ folder puts its files on the Bash tool's PATH, so an agent can call a CLI with a single Bash line and no schema at all. REA currently exposes its capability through MCP and CLI together, and the context cost of each path has not been compared.
- proposal: Measure the schema cost of the MCP server (count the tokens of the tool definitions it sends, from the init or /context output) against the cost of an equivalent Bash call to the bundled CLI. Where the CLI covers a task, the skill should direct the agent to it and keep the MCP server as a fallback. Keep bin/ within the plugin's own root (CLAUDE_PLUGIN_ROOT rules apply).
- expected gain: Removes the MCP schema from the context for the tasks that the CLI can do. The expected saving is the full MCP tool-definition token cost for those tasks, which must be measured. Output size still needs the Bash limits below.
- effort: medium
- risk: claude.ai and Cowork do not install a plugin that has a bin/ folder, so a bin-only design would lose those hosts. Also, the Bash PATH may not include a CLI that is not installed. Judge it with a test in each host: a plugin install and a run that calls rea through Bash.
- judge: Measure the token count of REA's MCP tool definitions in one session, then run the same 10 tasks through the Bash path. Compare input tokens. The check is one tokens-of-schema measurement plus 10 runs, with a second install test on claude.ai as the host check.

### Keep REA's tool output inline below the 30,000-character Bash limit, and return a file handle with a preview beyond it

- problem: A valid Bash result over about 30,000 characters is saved to a file with only a 2,000-character preview inline, and a failed result is cut to about 10,000 characters. A hook's context output is cut at 10,000 characters. If REA prints a whole target listing, the agent may see only the preview and then has to read the file. The MCP output limit (MAX_MCP_OUTPUT_TOKENS) was not confirmed from the docs, so MCP output behaviour is unknown.
- proposal: Have REA's CLI and tools paginate and return a summary with a handle (a path or an id) and a count, then let the agent page in the rest with a second call. Keep every single output under about 10,000 characters for the default case. Use the documented Bash and hook limits as the design targets, and confirm the MCP limit before relying on it.
- expected gain: A predictable context bill per call and no silent truncation. The judge measures it directly: the number of characters each REA call returns, and whether the agent reaches the answer in the same number of turns.
- effort: medium
- risk: More calls per task. An agent that pages too often costs more turns. Test the balance on large targets.
- judge: On one large target, record the characters per call and the number of turns to reach a verified answer, before and after. Expect fewer characters in any single call and no increase in turns beyond a small margin. The check is about 5 runs on a large target.

### Gate the clone-run verdict on structured output and on the init event

- problem: A verdict from a headless run is only as good as its parsing. A run that declines or fails to load REA produces no structured_output field, and a run whose MCP server did not connect still exits 0. Both cases can look like a successful verdict to a script that does not check them.
- proposal: In the referee harness, call `claude -p --output-format json --json-schema <verdict schema>`. Fail the run if structured_output is missing, and fail the run if the stream-json init event has a non-empty plugin_errors or mcp_server_errors array, or if REA shows status other than connected in mcp_servers. Read cost from modelUsage, which includes subagents, not usage.
- expected gain: Silent failures become visible, and the cost figure is correct when subagents run. The judge is a count of false passes.
- effort: small
- risk: The schema must match the referee's real verdict shape, or every run will fail the schema check. Also, total_cost_usd is an estimate and must not be used as a bill.
- judge: Inject three faults in a test run: a bad --mcp-config entry, a missing plugin path, and a declined task. Check that each one fails the harness. The check is three runs.

### Use a hook to stop destructive calls in each agent role, scoped by agent_type

- problem: The team playbook's seven roles should not be able to run every REA command. A plugin's subagent ignores its own hooks and permissionMode frontmatter, so role limits written there do not apply. The plugin's hooks/hooks.json does run inside subagents, and PreToolUse can deny a call. This is the working route, but REA has not used it.
- proposal: Put role limits in the plugin's hooks/hooks.json as PreToolUse matchers with an `if` clause (permission-rule syntax, e.g. Bash(rea *)) that checks agent_type from the hook input. Use permissionDecision deny for calls outside a role's allowed set. Treat it as a guardrail, not a security boundary, because the `if` field is best-effort and the permission system is the hard limit.
- expected gain: Each role is limited to its own tools, which catches wrong-role calls. Judge the saving as the number of blocked calls in a trial, not as tokens.
- effort: medium
- risk: The `if` field is best-effort for complex Bash input. Hooks also need the project trust dialog for project-level subagents, so a -p run must set trust or use --bare with the plugin loaded (but note bare mode drops plugin hooks).
- judge: Run each of the seven roles on a task that tempts a forbidden call, and count the denials. The check is seven runs. Confirm that a plugin-level hook fires inside a subagent (agent_type present in the hook input).

### Make REA's session state survive reset through CLAUDE_PLUGIN_DATA and --resume

- problem: CLAUDE_PLUGIN_ROOT changes on every plugin update, so any run state written there is lost. A session that is interrupted with SIGTERM (exit 143) leaves its in-progress turn unrecorded, and -p runs do not wait for MCP tasks. The clone-run evidence and the referee's state need to survive a reset.
- proposal: Store clone-run evidence, the comparer's output and the referee's state in CLAUDE_PLUGIN_DATA, which survives plugin updates. Resume an interrupted run with --resume <session_id> and send SIGINT, not SIGTERM, to end a turn cleanly. Use --session-id to name a run in advance.
- expected gain: A run that is reset or interrupted can continue from its last recorded state rather than restarting. The judge is whether a resumed run reaches the same verdict.
- effort: small
- risk: Plugin data is deleted when the plugin is uninstalled from its last location, unless --keep-data is used. Document this for users.
- judge: Kill one clone run mid-turn with SIGINT and with SIGTERM, resume each one, and compare the verdicts with an uninterrupted run. The check is three runs.
