# census-cli-output

## Summary

I ran 169 first-run CLI calls (99 of the 207 commands, 68 with a successful run) on 20 small real inputs, then 144 economy variants and 19 typical mistakes; 27 commands answered provider-unavailable and were measured only as errors. The median successful answer is 6,075 bytes (about 1,900 real tokens), but the tail is extreme: 58 of 121 exceed 2,000 tokens, 22 exceed 8,000, 7 exceed 100,000, and the largest is 15.9 MB (about 5.9 million tokens) for a 27 KB JavaScript file. The trial's outliers are typical of their commands, not accidents: analyze-javascript-application prints 24.9 KB for console.log("hi") and 250 to 1,300 times its input for anything larger, and the 3.3 MB case reproduced exactly (3,295,901 bytes). Most of those bytes are not the answer: the median share of plain answer values is 16%; the rest is 64-hex identifiers (45% of the JavaScript result), exact repeats (objdump and gdb results carry every byte twice), limitation text, envelope and key names. REA already has good economy machinery (summary with saved Evidence, 58 analysis views, --filter-output, paging, CSV) and it works: the same answers come back in 99 to 2,400 bytes. But all of it is opt-in, 141 of 207 commands have no size control, a summary needs a fresh file path, and the installed skill never mentions the global flags while its one CLI example is the megabyte form. Three controls mislead: --detail summary on objdump still prints 177 KB; TOON, the default format, costs a median 7% more real tokens than JSON while REA's own counter reports 12% fewer; --token-limit keeps the head of the document, which is provenance, and is refused with --json. The economical path also fails open: a summary command whose output file already exists prints the complete Evidence inside its error (1,022,734 bytes for a 2.3 KB bundle, 273,626 bytes when a referee capture command is run twice). In the clone-run loop the referee's printed capture command returns 25.5 KB each time, 88% of the 32,166 tokens one scenario costs, and one existing filter brings it to 341 bytes; a ten-item not_done verdict is 11,126 characters with exit 1, and this harness cut 1,137 characters out of its middle. Recommended default: one 6,000-byte budget at the single CLI result writer, where smaller results pass unchanged and larger ones are saved complete to a file and replaced by an answer-first digest; simulated on the 121 successful outputs, 61 become digests of at most 2,754 bytes and total first-answer bytes fall from 24.8 MB to 293 KB with nothing lost. Token figures use REA's estimator (tokenx) and a real BPE tokenizer (o200k_base); Claude's own tokenizer was not measured.

## Opportunities (10)

### One output budget at the CLI writer: save the complete result, print an answer-first digest

- problem: Nothing bounds a first answer. 58 of 121 successful first calls exceed 2,000 real tokens, 21 exceed 30,000 characters (Claude Code then shows a 2,000-character preview that is all provenance), the largest is 15.9 MB, and 141 of 207 commands have no size control. Every existing control is opt-in and needs prior knowledge of flags, view kinds or key paths.
- proposal: In src/cli/cliResultOutput.ts (write, reached by every command through src/cli/runCliCommand.ts) apply a default budget of 6,000 bytes to the rendered document. Under it, print as today. Over it, write the complete document to a content-addressed file (the --evidence_output path when given, otherwise a per-user evidence directory) and print a digest: result scalars, the ten largest key paths with row counts and row keys, limitation count, file path, bytes and sha256, and three exact follow-up forms. --detail complete, a --budget flag or REA_OUTPUT_BUDGET, and stdout redirected to a regular file keep today's bytes. Start with the generic digest (scripts/digest-prototype.py is the sizing prototype), then add command-owned briefs for the ten most used first commands.
- expected gain: Simulated on the 121 successful outputs: 60 unchanged, 61 become digests of median 1,498 B and at most 2,754 B; total first-answer bytes 24.8 MB -> 293 KB; largest first answer 5,999 B; the 113 non-JavaScript rows fall from 860,901 to at most 162,542 tokens (-81%). The digest also makes result key paths discoverable, which no schema does today.
- effort: medium
- risk: Changes what --json prints on a pipe for large results, so scripts that pipe complete Evidence into jq need --detail complete or a file redirect; upstream may prefer it opt-in first (an environment variable the skill and the referee's printed commands set). Files in a temp directory need a retention rule, and anything marked with --sensitive-value must stay out of them as it stays out of output today.
- judge: Rerun the census harness (specs/*.jsonl, 169 calls, about 6 minutes): assert no stdout above the budget, every digest's sha256 equals its saved file, and the answer marker of answer-position.tsv is inside the first answer for 24 of 24 questions (16 of 24 today).

## Shared root causes

1. Complete Evidence is the default and stdout is the only sink: 39 of 41 --detail commands default to complete; a summary needs a file path that must not exist.
2. Provenance first, answer last: Evidence starts with evidence_id, subject, provider, parameters; any head cut (token limit, a harness preview) keeps the least useful part. The answer marker lies beyond the first 6,000 bytes in 8 of 24 checked outputs.
3. Identity by 64-hex digest on every node, edge and row: 45% of graph results, 30-45% of inventories, 39% of guidance search.
4. Repeats: raw/normalized mirror, nested Evidence envelopes, the same limitations at two or three levels, bodies per request, two commands for one document.
5. Row data as arrays of objects with full keys and nulls (keys are a median 17% of bytes, 50% for the page inspector).
6. Binary and text payloads inline as base64.
7. Failure documents are unbounded and exempt from filters.
8. The controls are undiscoverable: no result schema, 58 view kinds behind a 134 KB schema, flags absent from the skill, the estimator and the default format point the wrong way.

## Default policy (first answer within budget, full result always reachable)

- Budget: stdout at most 6,000 bytes (about 2,000 real tokens of JSON), stderr at most 300 bytes on success, any error at most 1,500 bytes. 6,000 bytes sits just under today's median (6,075), so about half of all answers pass unchanged, and it is under the 10,000-character ceiling Claude Code applies to failing commands.
- Over budget: write the complete document to a content-addressed file and print a digest: status or verdict, result scalars, the ten largest key paths with row counts and row keys, limitation count, file path, bytes, sha256, and exact follow-up commands. No truncation anywhere.
- Same rule on failure: partial Evidence goes to a file that the error names.
- Opt out explicitly: --detail complete, a --budget value, or stdout redirected to a regular file.
- One place to enforce it: src/cli/cliResultOutput.ts.
- Simulation on the 121 successful outputs: 60 unchanged, 61 digests (median 1,498 B, max 2,754 B), total 24,792,993 -> 292,752 bytes, largest first answer 5,999 B.
