# census-mcp

## Summary

REA's full catalogue is 263 tools in one 352 KB tools/list page: 97,146 tokens by REA's own estimator (tokenx) and 78,806 by a real BPE tokenizer (o200k); the part a model can see (name, description, input schema) is 87,758 / 70,015, and the server instructions add 627 / 488. A client pays that only if it loads every definition: Claude Code defers MCP tools by default and holds names plus instructions (about 3,300 tokens for REA), and upstream's own recorded Codex trial measured +3 input tokens with all REA tools enabled, so the design doc's "97,000 tokens per agent" does not hold for the two main clients. The context goes to results instead: the same ten-call task returns 12,136 tokens when every call asks for a summary and 94,516 (118,999 real) with default arguments, because one static JavaScript analysis of a 1 KB app returns 292 KB inline. One of the four always-listed tools, get_evidence_bundle, returns 351 KB (96,832 tokens) by default after three small calls, and binary_session's default status costs 5,700 to 6,400 tokens. Even the frugal replies are mostly envelope: 47% of their bytes are limitation lists that each reply states two or three times, a one-row page is 7,850 bytes around a 136-byte row, and SHA-256 handles are 23% of the real tokens. Every successful result is also sent twice on the wire (text equals structured content), which doubles transport but not context in Codex. In the catalogue, schemas are 49% and descriptions 35%; nothing is shared by reference and mechanical noise removal saves only 6.4%, so schema trimming is a small lever. REA already has a progressive catalogue (hot-cold: 5 tools, 2,066 tokens) that completes the ten-call task, but it needs a client that refreshes tool lists, answers a cold call with a 91-byte "disabled" error and no hint, keeps every search hit loaded (28 tools after 15 searches) and returns nothing for 4 of 15 natural-language queries. A prototype lazy front (find, describe, call) over the unchanged server listed 7 tools (2,063 tokens), never changed the list, and finished the ten-call task including discovery in 17,158 tokens against 100,521 for a client that loads everything. The CLI route costs about the same as the lazy routes (3,779 tokens of per-command help plus 11,303 of output), but it writes progress JSON to stderr (21,384 tokens for a 100-file app whose answer is 2,533) and the clone-run scout card runs the JavaScript analysis with default detail. REA's token estimator is off by +23% to -39% against a real tokenizer depending on content, so it cannot be the judge of token work. The changes that cut the most for the least risk are therefore on the result side (the scout card, bounded default replies, quiet CLI progress, stating limitations once), then fixes to hot-cold, then a lazy gateway for the clients that neither defer nor refresh.

## Open questions (10)

- Real Claude token counts for the catalogue and the ten-call task were not taken: they need the count_tokens API, and the rules for this audit forbid sending this machine's content to an outside service. Anthropic's guidance says OpenAI-family tokenizers undercount Claude by 15-20% or more and the current Claude tokenizer uses up to 1.35 times as many tokens as the previous one, so the o200k figures here are likely low for Claude. One free API call by the owner would settle it.
- What Claude Code forwards to the model when a result has both text and structured content, and what its 25,000-token and 50,000-character thresholds measure, is not documented; user reports say structured content only. It decides whether REA's doubled wire payload ever reaches context there.
- Which of the other clients REA sets up (Cursor, Gemini CLI, VS Code, Kimi Code, OpenCode, Trae and others) defer tool definitions or refetch on list_changed could not be checked: modelcontextprotocol.io, developers.openai.com and a third-party client survey were outside this session's allowed network. The value of the lazy gateway depends on that answer.
- The design doc's reason for CLI-only clone runs has two parts. The catalogue part does not hold in Claude Code or Codex; the other part (one active target and one Evidence store per server, a second agent retargets the first) was not re-tested here. Should the synthesis revisit MCP for roles that work in one session?
- Does a hot-cold refresh rebuild the prompt cache in Claude Code when tool search already keeps definitions out of the prefix? Not measurable without a live session.
- Search quality needs a labelled set of task phrasings with expected tools. The any-word ranking in the prototype removed three of the four zero-result queries but ranked inspect_keyed_archive above inspect_artifact for 'inspect zip archive contents', and neither it nor discover_tools puts analyze_javascript_application in the top three for 'electron app'.
- What reply budget is right, and should it count characters or tokens? 40,000 characters stays under Claude Code's file threshold; a lower figure such as 12,000 would also summarise the 15 KB inventory.
- Browser capture replies were not measured (no browser was run, to keep the machine light); the design doc puts captures at 350 KB to 1 MB, so capture_browser_scenario's default reply size over MCP and the CLI is a gap in this census. Native provider tools could only be measured in their failure path (no Ghidra or IDA).
- Whether the fork wants a gateway at all, given upstream's explicit position against one and the effect on per-tool approvals; the front-process form keeps the server core identical to upstream if it does.
- Codex runs MCP tools from code it writes; with output schemas off the model cannot know a result's shape before seeing one. Would a short result-shape line in each tool's contract (where the answer lives, for example normalized_result.items) let code-mode clients filter replies before they reach context?

## 10. How a lazy mode would work in this server

Today: REA_MCP_TOOL_CATALOG_PROFILE=hot-cold (src/config/mcpToolCatalogProfile.ts:6) makes createServer.ts:643 and main/deferredRuntime.ts:226 call enableProgressiveCatalog(), which disables every tool outside four hot names (ProgressiveToolCatalog.ts:51-58) and registers discover_tools; discovery re-enables matches and the SDK sends one list_changed. The SDK uses one `enabled` flag for listing and for calls, so a cold tool cannot be called.
A lazy profile needs: (1) leave in-scope tools enabled; (2) filter tools/list responses to the hot set and meta-tools in ErrorEvidenceTransport, where output schemas are already rewritten; (3) rewrite an inbound call_tool {name, arguments} into a tools/call for that name before SDK dispatch, so validation, admission, error normalisation, target-content marking and cancellation run under the real tool name; (4) answer find and describe from the recorded catalogue the deferred server loads at start (catalog.tools, catalog.toolFamilies); (5) a new enum value and its own identity policy beside progressiveCatalogIdentity so the full and hot-cold digests do not move; (6) teach doctor, setup and status the value (mcpDoctor.ts:627-653, contracts/catalog/mcpDoctorCatalog.ts, cli/setupCommands.ts:104-107, application/DirectAnalysisStatus.ts:57). The alternative with no core change is a front process, as prototyped.
Stays compatible: the default catalogue and digest, hot-cold, family scope, canonical validation, Evidence. Changes for an opted-in user: tool approvals attach to the gateway names. Free today: family scoping, hot-cold where the client refreshes, and client-side deferral in Claude Code and Codex.
